# 일본 소·중형 설계사무소 파일럿 계획

2026-09-23. 공개자료 조사 이후 필요한 현장 검증 설계다. 인터뷰·관찰·고객 도면 수집은 **아직 수행하지 않았다**. 아래 인원·표본·목표는 모집 계획이며 시장 통계가 아니다.

## 1. 먼저 확인할 가설

| 가설 | 관찰할 행동 | 기각 또는 변경 조건 |
|---|---|---|
| 제출 직전 점검이 반복 부담이다 | 실제 최근 제출 2회의 작업 순서와 수동 확인 기록 | 이미 회사 도구로 충분히 해결되거나 업무 비중이 작음 |
| 이전 검토를 이어 가면 도움이 된다 | 반복 경고를 다시 판단한 횟수, 보류/제외 사유 재사용 | 기록 비용이 재검토 절감보다 큼 |
| 수정 지시 추출 AI가 유용하다 | 원문→작업목록 수동 시간 vs AI 초안 검토·수정 시간 | 누락 증가 또는 검토 시간이 더 길어짐 |
| 회사 프로필을 설정할 수 있다 | 실제 표준의 존재, 담당자의 매핑 성공 | 사무소별 변동이 심해 설정 유지 비용이 큼 |
| 소규모 사무소도 API 연결을 운영할 수 있다 | 계정·청구 책임자, 키 등록/폐기, 전송 정책 이해 | 연결·비용 관리가 제품 가치보다 부담이면 관리형 옵션 평가 |

## 2. 모집과 자료

목조 단독주택 중심 3~5개 사무소에서 각 2회 이상의 검토/제출 주기를 관찰한다. 대표가 직접 검토하는 곳과 작도·검토 담당이 나뉜 곳을 포함하고, 가능하면 다인 중형 사무소 1곳을 비교군으로 둔다. 규모별 차이는 측정 후 기술한다. 공무점 설계부는 독립 고객군으로 표시한다.

필요 자료는 회사가 제공을 허용한 도면 복제본 10~20세트, 그중 가능한 이전/수정본 쌍, 회사 레이어/문자 규칙, 수정 지시 샘플, 사용 Jw 버전·출력 방식이다. 숫자는 목표이며 확보 여부를 기록한다. 외부협력사 자료는 해당 사무소의 반출 권한도 확인한다. 고객명 삭제만으로 도면이 비식별화됐다고 간주하지 않는다. 최초 조사는 사무소 내부 PC와 로컬 데이터로 수행할 수 있어야 한다.

## 3. 인터뷰보다 우선할 관찰 질문

- 마지막으로 외부에 보낸 도면 묶음에서 어떤 파일이 기준본인지 어떻게 결정했는가?
- 적입·전화·메일·PDF 중 수정 지시는 어디로 들어왔고 어디에 남았는가?
- 누가 수정했고 누가 반영을 확인했는가? 보류한 지시는 어디에서 다시 찾는가?
- Jw의 데이터 정리·파일 비교·속성 변경이나 기존 외부변형으로 이미 해결하는 부분은 무엇인가?
- 레이어 이름·번호·그룹 축척은 회사 표준인가, 담당자·협력사마다 다른가?
- 도면 내용을 바꾸지 않고 표시만 다른 중복/짧은 선의 정당한 사례는 무엇인가?
- 기관 지적사항에 대해 원문, 답변, 수정 페이지의 대응을 어떻게 관리하는가?
- 평면·입면·建具表의 동일 창호를 무엇으로 식별하는가? 같은 번호가 다른 층에 재사용되는가?
- 사무소 내부 공유 폴더·NAS·OneDrive에 동시 작업이 있는가? 최신본 충돌은 어떻게 처리하는가?
- 어떤 도면은 클라우드에 전송할 수 없는가? API 청구·키·보존 조건을 누가 결정하는가?
- 설치·제거·업데이트를 누가 수행하며 일반 사용자 권한으로 가능한가?
- 지난달 사용한 반복작업 도구의 비용과 실제 계속 사용하는 이유는 무엇인가?

법적 적합성 판정·구조 안전 확인을 사용자 조사 답변만으로 자동화 규칙으로 만들지 않는다. 사람이 전문 판단한 사례도 geometry ground truth와 별도로 관리한다.

## 4. 비교 실험

첫 1회는 현재 방식 그대로 관찰한다. 비교 시에는 난도가 유사한 과제를 묶고 도구/기존 방식의 순서를 교차 배정한다. 같은 도면을 두 번 보면 기억 효과가 생기므로 모든 향상을 제품 효과로 계산하지 않는다. 검토자가 정답 목록을 알게 된 자료는 숨김 테스트로 다시 쓰지 않는다.

| 측정 | 정의 |
|---|---|
| 전체 작업시간 | 자료 준비+실행+경고 판단+수정+재검토+기록. API 대기 중 다른 업무 시간과 active time 별도 |
| task recall | 전문가가 합의한 원문 업무 중 올바르게 추출한 업무 / 전체 원문 업무 |
| task precision | 올바르게 추출한 업무 / 추출한 전체 업무 |
| 규칙 precision/recall | 규칙별·객체형별로 보고; 미검사 영역은 recall 분모와 별도 coverage로 공개 |
| 오탐 부담 | 의도된 표현을 오류로 받은 건수와 처리시간 |
| 기록 일관성 | 보류·제외 사유와 변경된 scope/rule에 대한 재확인 여부 |
| 수정 안정성 | 승인 밖 변경·속성 손실·취소 실패·Undo 실패 건수 |
| 고객 가치 | 반복 사용, 다음 실프로젝트 사용 의향, 실제 유료 제안 수락 여부 |

잠정 목표: 검토 총시간 중앙값 30% 감소, advisory 규칙 precision 90% 이상, 추출 task precision/recall 각 95% 이상. 표본 수·분모·분산·사무소별 결과와 함께 보고한다. 위험한 쓰기 결함은 단 1건이라도 해당 버전 쓰기를 중단하고 원인을 해결한다. 목표를 달성하기 위해 경고를 숨기거나 검사 범위를 몰래 줄이지 않는다.

## 5. ROI와 가격 실험

검증 전에는 월 구독 가격을 확정하지 않는다. 기본 가설은 사무소 단위 로컬 제품 라이선스와 선택적 API 비용 분리다. 장기적으로 지원·규칙 업데이트의 반복 가치가 확인되면 연간 계약을 비교한다.

```text
월 순절감 시간 = 작업횟수 × (기존 평균시간 − 도구 포함 평균시간)
                 − 추가 설정/유지/교육시간
월 기대가치 = 순절감 시간 × 사무소가 제시한 시간당 비용
              − API/지원의 추가 비용
```

회수한 시간을 실제 청구 매출 증가로 동일시하지 않는다. 불량·사고 예방 금액을 근거 없이 합산하지 않는다. 예산 시뮬레이션은 작업 수·입력/출력 토큰·현재 공급자 단가·재시도·동시 사용자 수를 변수로 하며 과거 단가를 고정하지 않는다.

가격 실험은 기존 작업과 비교한 효용을 경험한 뒤 진행한다. 무료 체험에서 '좋다'는 응답과 유료 사용 약속을 구분한다. 기존 무료 Jw 기능/외부변형을 쓰는 비용도 대안으로 보여 준다.

## 6. 설치·운영 수락

사무소 직원이 설치→Jw 진입→실제 선택 검사→검토 저장→재검토→CSV 반출을 도움 없이 완료하는지 본다. 15분 내 첫 읽기 전용 검사를 초기 목표로 두되 실측 전 성과로 광고하지 않는다. 키 설정은 핵심 로컬 작업과 분리한다.

일반 사용자 권한, 일본어·공백 경로, IME, 100/150/200% DPI, 네트워크 차단, API 키 취소, 데이터 삭제·백업·이전 버전 복구를 시험한다. SQLite live DB를 SMB/OneDrive 공동 파일로 두지 않는다. 단일 PC에서는 local app data에 저장하고 공유는 export/import 묶음으로 시작한다. 다중 사용자 원장과 강한 비용 한도는 office gateway의 별도 역할이다.

## 7. 결정과 보고

각 사무소의 사례 보고는 프로젝트 식별정보 없이 표본 수, 실제 단계, 기존 대안, 소요시간, 발견·누락·오탐, 연동 실패, 비용, 반복 사용 여부, 다음 결정을 기록한다. 민감 원문을 보고서에 자동 첨부하지 않는다.

조사 결론으로 선택 가능한 결정은 계속 개발 / 대상 업무 변경 / AI task 보류 / 쓰기 제한 유지 / 파일럿 중단이다. 고객 요청이 많다는 이유만으로 구조·법규 자동화를 첫 제품에 섞지 않는다. 제품 판단은 [v0.2 계획](product-plan-v2.md)과 [로드맵](roadmap.md)에 반영하고 다음 스프린트 범위를 다시 고정한다.
