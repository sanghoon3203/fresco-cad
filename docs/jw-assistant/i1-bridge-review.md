# I1 bridge review (read-only)

Reviewed `addons/jw-assistant/bridge/*`, `tests/bridge_capture.test.ps1`, and the installed `C:\jww\JWW_SMPL.BAT` decoded as Windows code page 932. No Jw_cad UI was launched for this review. The existing test passed with `pwsh -NoProfile -File tests/bridge_capture.test.ps1`; it creates and removes only a unique directory under the system temporary directory.

## Verified wrapper and sample contract

- Both BAT files put `goto FRESCO_CAPTURE` on line 2, the seven active Jw directives on lines 3–9 in this exact order: `#jww`, `#cd`, `#hf`, `#h1`, `#hc`, `#g1`, `#e`. They then run `Capture-JwTemp.ps1` at line 15 with `-SourcePath "%~dp0JWC_TEMP.TXT"`, `-CaptureRoot "%LOCALAPPDATA%\FrescoCAD\jw-captures"`, executable path, and wrapper path. CMD skips the directive block; Jw reads it as BAT metadata. No wrapper command writes or deletes `JWC_TEMP.TXT`.
- The SJIS wrapper is valid strict CP932, 644 bytes, without BOM. The UTF8 wrapper is valid strict UTF-8, 672 bytes, **without BOM**. Both contain Japanese `#hc` text.
- Installed sample lines 29–31 say `#cd` puts `JWC_TEMP.TXT` beside the selected BAT. Lines 37–50 define `#h1` and require `#hc` after it; lines 64–67 define `#g1`; line 125–126 ends BAT settings with `#e`. Lines 289–293 say Jw writes `hq` first and reports 未実行 (not executed) if it remains on return; lines 514–523 distinguish `hq` from destructive `hd`.
- The [official 10.01.2 change note](https://www.jwcad.net/versioninfo.htm) says Jw chooses external-output encoding from the BAT encoding and displays the BAT classification in its chooser. In the separate native gate, the chooser displayed **both checked-in wrappers as `[S-JIS]`**, including `FRESCO_CAPTURE_UTF8.bat`. This is direct evidence that the no-BOM UTF8 wrapper is **not recognized as UTF-8 by that installed Jw 10.3.6 chooser**. A Jw UTF-8 output claim for that wrapper is unsupported until its recognition is fixed and retested. The CP932 wrapper's chooser label agrees with its bytes.

## Concrete I1 handoff risks and mitigations

1. **Shared live input and wrong-session capture.** Both BATs reside in the same directory and use the same `JWC_TEMP.TXT` through `#cd`. The helper's `FileShare.Read` protects bytes only once it opens that path (`Capture-JwTemp.ps1:77–83`); it cannot prevent another Jw invocation overwriting the common path before that open. Unique output bundle IDs (`:268–275`) isolate completed copies, not the Jw-to-helper handoff. Run one external transformation at a time per wrapper directory or use a distinct verified directory per session. The browser importer should open completed bundles, never the live `JWC_TEMP.TXT`, and should label a bundle's originating Jw session as unverified unless the native gate can establish it.
2. **UTF-8 wrapper misclassification.** The installed chooser's `[S-JIS]` label for the no-BOM UTF8 BAT conflicts with the intended UTF-8 branch. Since Jw chooses output encoding from its BAT classification, route the current native gate through the CP932 wrapper. Fix UTF-8 recognition in a staged copy and observe the chooser label plus captured Japanese bytes before enabling UTF-8 as a supported variant. Do not infer the Jw output codec from the wrapper filename or the helper's wrapper-byte detection.
3. **Ambiguous source codec.** `Get-TextCodec` (`:136–179`) tries strict UTF-8 before strict CP932. Some byte sequences are valid in both: `68 71 0D 0A C2 A9 0D 0A` is `hq` followed by `©` in UTF-8 and `hq` followed by `ﾂｩ` in CP932. It reports `utf-8` even if a CP932 producer emitted the latter. Treat `metadata.source.codec` as a heuristic; for the importer, require explicit user/host codec selection when both are plausible and retain raw bytes. Strict decode plus parse diagnostics should fail closed rather than silently replace characters.
4. **Incomplete bundle visibility.** The script writes `JWC_TEMP.TXT` and then writes `metadata.json` directly (`:275`, `:323`), with no completion marker or atomic rename. A browser watching the capture root can see the folder or a partial metadata file before the helper finishes. Offer only bundles with parseable metadata, an existing capture, matching recorded lengths and SHA-256 hashes; retry or skip incomplete entries. Treat the safety flags in metadata (`:314–317`) as script assertions, not proof that Jw geometry or Undo state was unchanged.
5. **Read-only boundary is narrower than host immutability.** The helper opens its source with read access and a restrictive share mode, copies exact bytes, verifies the copy hash (`:72–118`, `:262–280`), and the test confirms these properties on a synthetic read-only file. The test does not launch Jw or verify geometry, saved drawing bytes, layer state, or Undo. Preserve `hq` unchanged, keep the browser importer free of any Jw write path, and reserve host immutability claims for the native gate.

The existing test checks a CP932 source fixture, one UTF-8 wrapper metadata path, both wrapper text encodings, rejection of `C:\jww` as a lexical capture destination, and an exclusive source lock. It does not check Jw's BAT encoding classification, parallel invocations, bundle publication timing, or real host state. These gaps are tied to the observations above; they do not invalidate the passing byte-copy test.
