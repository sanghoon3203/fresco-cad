## 1. 이번에 바꾼 결정

첫 제품의 약속은 **Jw_cad를 유지하면서 제출 전 점검과 수정 확인에 드는 반복 작업을 줄이는 것**이다. 소규모 목조주택 사무소를 첫 고객으로 하고, 여러 담당자가 도면을 인수하는 중형 사무소까지 같은 데이터 계약으로 확장한다. 인원수만으로 업무를 일반화하지 않는다.

| 기존 계획 | 개정 결정 | 이유 / 근거 |
|---|---|---|
| 선 검사 → 자동수정 → 검토 기록 | 읽기 전용 검사 + 검토 기록 → 현장 사용 → 검증된 쓰기 | 원본 수정 없이도 유용한지를 먼저 확인; 실제 Jw 왕복 미시험 |
| 도면 비교를 유료 차별점으로 강조 | 기존 비교 기능 위의 판단 이력·재확인·제출본 연결 | Jw 기본 파일 비교와 변경 부분 작도 존재: [공식 이력](https://www.jwcad.net/versioninfo.htm) |
| AI 설명·자연어 작도 중심 | 수정 지시의 업무 항목화와 근거 확인을 첫 AI 기능 후보에 추가 | 사무소의 도면 검토 왕복 사례 및 기관의 보정 절차; 조사에서 도출한 제품 가설 |
| 회사 표준 학습 | 레이어·축척·문자·예외를 사람이 확정하는 회사 프로필 | 도면마다 설정·표현 차이; 과거 파일이 곧 정답이라는 전제 제거 |
| 단일 공급자 추상 인터페이스 | 실제 공급자별 차이를 가진 adapter + 공통 검증 + 사무소 정책 | OpenAI / Anthropic / Gemini의 API·보존·과금 조건을 별도 관리 |
| 초기부터 native 코어 이행 | 연동과 실측 후 설치형 기술 결정; 계산 코어는 하나 | Qt·JS·Rust에서 같은 규칙을 중복 운영하는 비용 방지 |
| 작업시간의 수치 가설 | 출처 없는 시간표를 제거하고 현장 측정 항목으로 전환 | 공개 자료로 Jw 작업별 평균시간과 절감률은 확인하지 못함 |

문서 우선순위: 기능·합격 조건은 [requirements.md](requirements.md), 구현 경계는 [architecture.md](architecture.md), 일정/출시 순서는 [roadmap.md](roadmap.md), 이번 변경의 의도와 업무 흐름은 본 문서다. 충돌 시 이번 v0.2 개정 내용을 기준으로 통합한다.

## 2. 조사에서 확인한 것과 아직 모르는 것

공식 기관·협회의 자료는 기본설계, 실시설계, 신청, 견적 검토, 공사감리, 인계로 이어지는 업무의 기준을 보여준다. [일본건축사사무소협회연합회 안내](https://www.njr.or.jp/data/general/kenchikupamph/njr_kenchiku_pamphlet.pdf). 사무소 블로그는 실제 프로젝트에서 검토가 왕복하는 사례를 제공하고, 강의는 작업 순서와 설정 의존성을 보여준다. 이 세 자료는 서로 다른 질문에 답한다.

- **확인된 업무 사례:** 프리컷 도면을 설계·시공·업체가 대조하고 수정본을 다시 확인하는 과정. [礒建築設計事務所, 2024-07-31](https://iso-aa.co.jp/blog/さがみ野の家　プレカット図チェック/).
- **확인된 제출 절차 사례:** BCJ는 전자 신청에 파일 형식·명명 규칙과 본신청 이후 추가·보정 절차를 안내한다. 이는 BCJ 절차이며 모든 심사기관 공통 규칙으로 하드코딩하지 않는다. [BCJ 안내](https://www.bcj.or.jp/inspection/confirm/elect/).
- **제품 추론:** 수정 요청과 그 반영 증거를 연결하면 반복 확인을 줄일 가능성이 있다. 실무 유용성과 지불 의향은 미검증이다.
- **미확인:** 일본 중소 사무소의 Jw 보급률, 업무별 평균시간, 특정 오작업의 발생률, 제품 가격 수용도. 강의 길이는 업무시간으로 사용하지 않는다.
- **조사 범위:** 공개 본문·강의 목차·공개 샘플을 선별 확인했다. 모든 강의를 수강하거나 커뮤니티 전체를 분석한 결과가 아니다. 블로그의 CAD 종류가 명시되지 않으면 Jw 사용 사례로 표시하지 않는다.

조사 근거: [업무 조사](research/japan-workflow.md), [Jw 연동·기존 도구](research/jwcad-integration-market.md), [API 공급자 조사](research/ai-provider-options.md), [추가 근거와 한계](research/evidence-ledger.md).

## 3. 고객 구분과 첫 사용 시점

| 고객 가설 | 업무 상황 | 초기 제공 | 나중에 추가 |
|---|---|---|---|
| 대표가 설계·검토를 겸하는 소규모 사무소 | 작업 중단 후 수정 사항을 다시 기억해야 함 | 개인 로컬 기록, 적은 초기 설정, 이전 검토 이어가기 | 원격 협업·중앙 관리 |
| 대표와 작도 담당자가 나뉜 사무소 | 지시·수정·검토 인수인계 | 수정 항목에 출처·담당·확인자·도면 버전 연결 | 조직별 승인 단계 |
| 여러 프로젝트를 병행하는 중형 사무소 | 파일 서버, 사내 표준, 외부 구조·설비 협력 | 프로젝트 분리, 프로필 버전, 파일 해시 기반 발행본 목록 | 사무소 gateway, 계정·권한·공통 비용 관리 |
| 공무점의 설계 부서 | 발주·현장·프리컷과의 연결 비중이 다를 수 있음 | 별도 파일럿군으로 관찰 | 동일 기능의 수요를 독립 평가 |

첫 사용 시점은 **사내 검토 또는 외부 전달 직전**이다. 일반 사용자는 프로젝트와 회사 프로필을 선택하고 Jw 외부변형으로 선택 범위를 넘긴다. 초기 제품은 한 PC에서 완결되고 사내 서버 설치를 요구하지 않는다.

## 5. 제품 흐름 A — 도면 검사와 재검토 (첫 출시)

1. **입력:** 사용자가 선택한 Jw 데이터, Jw/adapter 버전, 그룹별 축척·좌표계, 회사 프로필. 원본 바이트와 추출 범위를 보관한다.
2. **계산:** 지원 객체만 geometry/rule engine으로 검사한다. 미지원 객체·중단·선택 밖 범위를 CoverageReport로 반환한다.
3. **화면:** 위치와 측정값·허용값·규칙을 보여준다. `검사에서 발견되지 않음`과 `검사하지 않음`을 분리한다.
4. **판단:** 설계자는 수정 필요·의도된 표현·보류를 선택한다. 제외에는 범위·이유·규칙 버전을 남긴다.
5. **Jw 작업:** 최초 읽기 전용 버전에서는 설계자가 Jw에서 수정한다. 새 snapshot을 받고 재검사한다. writer 게이트 통과 후에만 정확 중복·0길이 정리 preview를 제공한다.
6. **확인:** 사용자의 범위 확인과 coverage 비교로 동일 범위·규칙을 확인했을 때 더 이상 발견되지 않은 항목을 해소 후보로 표시한다. 별도로 실행한 두 외부변형 선택이 동일 범위라고 자동 가정하지 않는다. 선택 밖으로 빠졌거나 매칭이 모호한 항목은 `확인 불가/재확인 필요`다.
7. **기록:** 원본/새 snapshot, 판단자, 규칙, 검토 결과를 로컬에 저장한다. 설계 적합 또는 발행 승인으로 자동 승격하지 않는다.

LLM은 이 흐름에 필수가 아니다. 선택적 설명도 엔진의 수치와 근거를 바꿀 수 없다.

## 6. 제품 흐름 B — 수정 지시를 확인 가능한 작업으로 (첫 AI 확장)

처음에는 사용자가 붙여 넣은 일본어 지시문과 지정한 문서 쪽을 사용한다. PDF 주석 추출, 스캔 OCR, 손글씨 인식은 독립된 입력 adapter이며 정확도를 별도 측정한다.

예시 입력: `W-07の幅を1500に変更。建具表と東立面も確認。高さは前回打合せ後に決める。`

- **AI 판단:** 폭 변경, 창호표 확인, 동측 입면 확인을 작업 초안으로 나눈다. 높이는 미확정으로 유지한다. W-07의 유일성·단위·대상 도면이 불명확하면 질문한다.
- **프로그램 처리:** 인용한 sourceSpan과 도면/창호 후보 ID를 확인한다. 동일 번호가 여러 층에 있으면 자동 매칭하지 않는다. 확정되지 않은 이전 회의 내용은 찾아낸 것처럼 채우지 않는다.
- **설계자 확인:** 원문 옆에서 초안을 검토하고 대상 도면·담당·완료 기준을 확정한다. AI 초안은 업무 지시로 자동 승인되지 않는다.
- **Jw 작업:** 설계자가 평면을 수정하고 재검사한다. 창호표와 입면은 사용자가 연결하거나 확인한 관계만 추적한다.
- **완료 확인:** 수치 대조가 가능한 항목은 엔진 증거를 첨부한다. 해석이 필요한 항목은 검토자가 직접 완료 처리한다. AI가 모든 관련 도면을 찾았다고 표시하지 않는다.
- **출력:** 변경대장·검토 결과를 CSV/JSON으로 내보내고, 답변 초안은 사용자가 확인한다. 메일·심사기관으로 자동 제출하지 않는다.

LLM 호출은 작업 목록 추출 1회부터 시작한다. 매 클릭·객체마다 호출하거나 다수 모델의 합의를 필수로 하지 않는다. 이 흐름이 시간과 누락을 실제로 줄이는지 [파일럿 계획](pilot-plan.md)으로 판정한다.

## 7. 제품 흐름 C — 제출본 점검과 인수인계

사용자가 지정한 JWW/PDF/CSV 파일 목록과 명시적인 도면번호·개정번호를 입력한다. 파일 해시, 필수 항목, 중복번호, 불일치한 개정, 남은 검토 업무는 로컬 엔진이 대조한다. JWW 내용 추출이 없으면 내부 내용을 검사했다고 표시하지 않는다.

제출 목록은 프로젝트 내부 draft/reviewed/issued 상태와 `누가 어떤 파일 버전을 발행 대상으로 선택했는가`를 기록한다. CAD 검사가 통과해도 제출 묶음 전체가 승인되지는 않는다. 기관별 파일 작성 규칙은 출처·버전·대상 기관이 붙은 설정으로 관리한다. 제출 기능 자체는 MVP에 없다.

저장 파일 hash는 다른 사용자의 미저장 Jw 캔버스를 탐지하지 못한다. 전달 직전에 파일과 기준 snapshot을 다시 확인하고, 미저장 내용이 반영된 제출본인지 사용자가 확인한다. 동시 편집 병합이나 전사 최신본 보장을 제공한다고 설명하지 않는다.

## 9. API 연결과 사무소 도입

관리자가 공급자·검증한 모델·청구 경로·전송 정책·예산을 설정한다. 일반 사용자는 `설명`, `수정 지시 정리` 같은 업무 기능을 선택한다. 고급 설정에서 모델을 바꿀 수 있지만 평가 미통과 조합은 실험 표시가 필요하다.

- **로컬 전용:** 키 없이 검사·검토·기록·CSV 작업이 가능하다.
- **사무소 BYOK:** 사무소가 계약한 API 키를 해당 Windows 사용자 보관소에 저장하고 native host에서만 사용한다. 제품 설정 파일·브라우저 저장소·Git·로그에 저장하지 않는다.
- **중형 사무소 gateway:** 직원 기기에 공용 API 키를 배포하지 않고 사무소 gateway가 비용·동시 사용·프로젝트 정책을 집행한다. 중앙의 강한 예산 제한이 필요하면 이 경로를 사용한다.
- **관리형 서비스:** 후속 유료 옵션. 제공자 청구·데이터 처리·운영 책임까지 별도 검증하고, BYOK 출시와 섞지 않는다.

사용자 AI 구독권과 API 청구를 같은 것으로 취급하지 않는다. 모델 이름을 화면에 넣었다고 계정 접근과 해당 기능 지원이 보장되는 것은 아니다. 모든 연결은 기능 탐지·작은 비민감 시험·평가 후 활성화한다. 현재 제품에는 API 연결이 구현되어 있지 않다.

구체 계약과 프롬프트: [AI 작업·평가 설계](ai-workflows.md), [공급자별 근거](research/ai-provider-options.md). 실제 화면 흐름과 ja/en 문구는 [사무소 온보딩 UX](office-onboarding-ux.md)를 따른다.

## 10. 출시 판단

출시 순서는 **읽기 전용 실제 연동 → 검토 이력 파일럿 → 최소 AI 작업 → 검증된 수정 반환 → 도면 세트 연결**이다. 쓰기가 지연되어도 읽기 전용 가치를 측정한다. AI API가 없어도 핵심 검사가 지속되어야 한다.

첫 파일럿에서 도구 실행과 판단까지 포함한 시간이 줄지 않거나, 실제 반복 사용 의향이 낮으면 기능을 더 늘리기 전에 대상 업무를 수정한다. 중복선 검사가 별 도움이 없고 보정 업무 관리만 유용하다는 결과가 나와도 제품 방향을 그 근거에 맞게 바꾼다.

다음 개발 항목, 의존성, 병렬 담당과 완료 기준은 [로드맵](roadmap.md)에 고정한다. 이번 조사 자체의 완료와 실제 제품 기능의 완료는 [조사 스프린트 보고](sprint-01-research-report.md)에서 구분한다.
